# PDF 도구 참고 분석 (REA, 2026-10-13)

iLovePDF를 기준 모델로 PDF 도구를 설계하기 위해, 공개 페이지를 REA로 **수동 관찰**했다.
별도 Chrome 프로필(디버깅 포트는 127.0.0.1)에서 페이지를 열고, REA가 DOM·접근성 트리·스크립트를 읽기만 했다(클릭·업로드·스크립트 실행 없음). 파일은 올리지 않았다.
코드·리소스·브랜딩은 가져오지 않았고, **도구 구성과 처리 구조**만 참고했다.

## 추론과 한계
- iLovePDF의 압축 알고리즘·품질 설정은 서버에서 동작하므로 브라우저 번들로는 알 수 없다(관찰 범위 밖).
- 편집 화면의 도구 막대는 파일을 올린 뒤에만 나타나서 관찰하지 않았다.
- 정적 분석은 스크립트를 실행하지 않으므로, 실제로 어떤 코드 경로가 실행되는지는 확인하지 않았다.

## 설계에 반영한 것
- **구조**: 도구 그리드 → 도구별 화면(업로드 → 옵션 → 처리 → 결과), 결과에서 “이 결과로 이어서” 다른 도구로 넘기기
- **차별점**: iLovePDF는 서버 처리, 우리는 오픈소스(pdf-lib·pdf.js)로 **브라우저 안에서만** 처리 → 파일 업로드 없음
- **제외**: 서버나 별도 엔진이 필요한 Office 변환·OCR·암호화는 흉내 내지 않고 “제공하지 않음”으로 명시
