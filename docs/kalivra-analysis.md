## 1. Kalivra가 하는 일

| 영역 | 내용 | 코드 |
|---|---|---|
| 데이터 | 엔티티(캐릭터) × 스탯. 스탯 = `{ b: 기본값, g: 레벨당 증가 }` → `b + (Lv − 1) × g` (선형만) | `calculator.getStatsAtLevel` |
| 아이템 | 대상 엔티티 목록 + 스탯 수정자(`add` / `mult`, 아이템 순서대로 적용) + 특성(트리거) | 같은 곳 |
| 규칙 수식 | 데미지 `a.atk * (100 / (100 + b.def))`, 명중 `a.acc - b.eva`, 전투력(CP) `atk*aspd*10 + hp*0.5 + …` — 기획자가 수식 문자열로 바꿈 | `projectDocument` 기본값 |
| 성장 그래프 | 엔티티별 Lv1~최대 레벨 CP 또는 데미지 곡선, 스냅샷과 겹쳐 비교(점선), 평균 변화율 | `renderer.runSimulation` |
| 전투 | 1:1 턴제. 명중(5~100% 고정 범위) → 데미지 수식 → 분산 → 치명타 → 트리거 → 체력 감소, 최대 200턴 | `battle.simulateBattle` |
| 트리거 | 전투 시작·턴 시작/끝·공격 전·적중·피격·빗나감·회피·치명타 × 조건(확률, 체력 n% 이하) × 효과(회복, 추가 데미지, 데미지 배율, 스탯 버프 n턴) | `battle.BattleSystem` |
| 몬테카를로 | 상세 분석 1만 회: 승률, 선공 시 승률, 평균 턴, 실현 치명·회피율, 턴당 데미지, 오버킬, 턴 분포·승리 시 남은 체력 분포 | `battle.runMonteCarlo` |
| 리그 | 모든 엔티티 쌍의 승률 행렬(한 레벨, 쌍마다 100회), 칸을 누르면 상세 분석 | `renderer` 리그 모달 |
| 구간 분석 | 최대 레벨을 초반·중반·후반 1/3씩 나눠 레벨마다 10회 전투한 승률 | `battle.runPhaseAnalysis` |
| 감시(Watchdog) | 레벨마다 엔티티 평균 대비 ±20%를 넘는 레벨 비율 → 50% 초과 CRITICAL, 20% 초과 WARNING, 약함 WEAK, 구간별 1위, **역전 레벨**(두 곡선이 교차하는 레벨) | `analyzeBalanceIssues`, `analyzeCrossovers` |
| 목표 역산 | "Lv20 CP = 1000"처럼 목표를 주면 한 스탯의 레벨당 증가(g)를 이분 탐색 | `solver.findGrowthValue` |
| 작업 안전 | `.kal` 프로젝트 파일, 스냅샷(이력), 아이템 세트, 일괄 편집 그리드, 잠금, Undo/Redo(main에서 명령 기반으로 정리) | `dataManager`, `commandManager` |
| 내보내기 | CSV, JSON, Unity(ScriptableObject C# + JSON zip), Unreal JSON, 리포트(PDF·이미지) | `renderer` |

REA로 확인한 앱 구조: 창 1개, IPC 채널 11개(창 조작·`.kal` 저장/불러오기·CSV/JSON 내보내기, 동적 채널 1개), localStorage `KAL_CUSTOM_PRESETS`(수식 프리셋). 계산은 모두 렌더러에서 돈다.

## 2. 잘못됐거나 위험한 부분 (코드 근거)

| # | 문제 | 근거 | 영향 |
|---|---|---|---|
| 1 | **공격 속도가 공격 횟수를 바꾸지 않음** | 매 턴 선공·후공이 한 번씩 공격하고, `aspd`는 전투 시작 때 누가 먼저인지 확률(`aspdA / (aspdA + aspdB)`)에만 쓰임 | aspd 2배 캐릭터도 같은 횟수로 때린다. 그런데 CP 수식은 `atk*aspd*10`으로 aspd를 크게 쳐서, **CP 그래프와 전투 승률이 서로 반대 결론**을 낼 수 있다 |
| 2 | 피격 트리거의 스탯 버프가 두 번 적용 | `OnHitTaken`을 두 번 처리하는데 허용 효과 목록 두 곳에 모두 `BuffStat`이 있음. 확률 조건도 처리마다 다시 굴림 | 피격 버프형 특성이 설계보다 2배 강하게 나온다 |
| 3 | 무승부를 패배로 셈 | 200턴 안에 안 끝나면 winner 없음 → A의 승리에 안 들어감. B 쪽에서 돌려도 마찬가지 | 탱커끼리 붙으면 양쪽 다 승률이 낮게 나온다. 리그 행렬에서 A→B와 B→A의 합이 100%가 아님 |
| 4 | **README의 "승률 신뢰 구간"이 구현되어 있지 않음** | 신뢰 구간·표준오차 계산 코드가 없음 | 리그 100회는 승률 50% 근처에서 95% 오차가 약 ±10%p, 구간 분석은 레벨당 10회(최대 레벨 20이면 구간 하나에 60~80회, ±11~13%p). 60/40 색 구분이 잡음에 좌우된다 |
| 5 | 감시 기준이 전투 결과가 아니라 CP 평균 대비 ±20% | `analyzeBalanceIssues` | 1번과 겹쳐, CP로는 OP인데 실제로는 지는 캐릭터를 OP로 경고할 수 있다. 상성(가위바위보)도 못 잡는다 |
| 6 | v1.0.1은 수식을 `new Function`으로 실행 + 창이 `nodeIntegration: true`, `contextIsolation: false` | `calculator.calculateValue`, REA 그래프의 BrowserWindow web_preferences(리터럴) | 남이 준 `.kal` 파일의 수식 칸에 코드가 들어 있으면 PC에서 그대로 실행된다. **main에서는 자체 파서(`formulaEvaluator`)로 바뀌었으니 v1.0.1 설치본은 남의 프로젝트 파일을 열지 않는 게 안전** |
| 7 | 성장은 선형뿐, 아이템 `add`/`mult`는 목록 순서대로 | `getStatsAtLevel` | 같은 아이템 둘의 순서만 바꿔도 결과가 다르다. 등비·구간 성장은 표현할 수 없다 |
| 8 | 명중률 하한 5%·상한 100%가 코드에 고정 | `Math.max(5, Math.min(100, hit))` | 규칙에서 바꿀 수 없다 |

## 3. 워크벤치와 비교

| | Kalivra | 워크벤치 지금 |
|---|---|---|
| 강점 | 엔티티·스탯·수식을 기획자가 정의, 전투 승률, 리그 행렬, 트리거, 스냅샷 비교, 엔진 내보내기 | 정확해(마르코프·동적 계획법) + 시뮬레이션 검증, 분위수, 민감도·반대 가정, 브라우저만으로 공유 |
| 약점 | 시뮬레이션만 있고 오차 표시 없음, 위 2번 표의 계산 문제 | **캐릭터 스탯·전투 승률을 다루는 탭이 없음**, 탭마다 데이터가 따로, 기준안 비교는 강화 탭뿐 |

→ Kalivra의 **문제 정의(엔티티 × 스탯 × 수식 × 승률)**를 가져오고, 계산은 워크벤치 방식(정확해 우선, 오차 명시, 반대 가정)으로 다시 만든다. 코드는 옮기지 않는다(라이선스: 수정 배포 시 저작권 표시 필요, 판매 금지). README에 참고 출처로 적는다.

## 4. 재설계: 새 탭 "스탯·전투 밸런스"

### 4-1. 데이터 모델
- **스탯 정의**: 이름·설명·최소/최대(예: 치명 0~100%). 명중 하한·상한도 규칙 값으로.
- **성장 방식**: 스탯마다 선형(`b + (Lv−1)g`) / 등비(`b × r^(Lv−1)`) / 표(CSV 붙여넣기, 레벨을 띄엄띄엄 넣으면 사이를 직선 보간 = 구간 성장).
- **수정자 적용 순서 고정**: `(기본 + Σ고정) × (1 + Σ%) × Π(곱연산)` — 순서에 따라 결과가 바뀌지 않게.
- **수식**: 데미지·명중·CP·(새) 행동 간격. `a.*`, `b.*`, `min/max/clamp/floor` 정도의 안전한 수식 파서(코드 실행 없음). 입력할 때 바로 검증해서 오류 위치 표시.
- 저장: JSON(머리 정보 + state, 다른 탭과 같은 형식), 공유 링크, CSV.

### 4-2. 전투 모델 (Kalivra 1번 문제 해결)
- **시간 기반**: 공격 간격 = 1 ÷ 공격 속도. A의 n번째 공격 시각 = n ÷ aspdA. 같은 시각이면 규칙(동시 타격 / 선공 우선)을 고른다.
- **정확해 (트리거 없는 기본 전투)**: 한 번의 공격 결과는 빗나감·적중·치명 세 가지(분산은 균등 구간을 k칸으로 나눔). 상대를 쓰러뜨리는 데 필요한 공격 횟수 N의 분포를 동적 계획법으로 구하고, A와 B의 N은 서로 독립이므로
  `P(A 승) = Σₙ P(N_A = n) × P(N_B ÷ aspdB > n ÷ aspdA)` 를 정확히 계산한다. 결과: 승률(오차 0), 처치 시간 분포, 승리 시 남은 체력.
- **시뮬레이션 (트리거·버프가 있을 때)**: 같은 시간 모델 + 이벤트 순서 고정. 트리거 효과는 한 번만 적용하고 확률 조건은 한 번만 굴린다. 무승부는 따로 센다.
- **검증**: 정확해가 있는 설정에서 시뮬레이션과 실시간 비교(강화·가챠 탭의 "계산 검증" 카드와 같은 형식). 테스트로 Kalivra 2·3번 같은 문제가 다시 생기지 않게 막는다.

### 4-3. 결과 화면
1. **레벨 곡선**: CP·초당 데미지·처치 시간(TTK) 곡선, 역전 레벨 표시(Kalivra의 교차 감지 그대로), 기준안 점선.
2. **CP와 실제 승률 차이**: "CP 수식이 실제 전투력을 얼마나 맞히나" — 레벨별로 CP 순위와 승률 순위의 상관(순위 상관), 어긋나는 쌍을 경고. Kalivra 1·5번 문제를 기획자가 직접 발견하게 하는 기능.
3. **승률 행렬**: 한 레벨에서 모든 쌍. 정확해면 그대로, 시뮬레이션이면 **95% 신뢰 구간(Wilson)**을 같이 표시하고, 구간이 50%를 걸치면 "차이 없음"으로 회색. A→B와 B→A는 한 번만 계산(합 = 100% − 무승부).
4. **구간 리포트**: 초반·중반·후반(경계는 직접 지정) 평균 승률·1위·역전 레벨 — 브리핑용 한 장 요약에 바로 들어가는 형식.
5. **감시 (전투 결과 기준)**: 어떤 구간에서 모든 상대에게 55% 이상 이기는 엔티티(지배), 상성 순환(A>B>C>A), 처치 시간이 너무 짧은(한 방) 쌍, 무승부 비율이 높은 쌍.
6. **분위수**: 처치 시간·남은 체력의 0.1%~99.9% (`js/lib/quantiles.js` 재사용).

### 4-4. 밸런스 도구 (워크벤치 방식으로 확장)
- **목표 역산**: Kalivra는 "Lv20 CP = 1000"만 가능. 여기서는 **"Lv20에서 A 대 B 승률 50%"**처럼 승률 목표로 한 스탯의 성장값을 이분 탐색(정확해 승률은 성장값에 단조라 바로 풀림).
- **민감도·반대 가정**: 스테이지 탭의 토네이도를 그대로 — 스탯·성장값마다 ±10%가 승률을 얼마나 바꾸나, 지배를 풀려면 무엇을 얼마나 바꿔야 하나.
- **아이템·특성 효과 분해**: 아이템을 하나씩 뺐을 때 승률 변화 → "이 승률의 몇 %p가 이 아이템 때문인가".

### 4-5. 다른 탭과 연결
- 스테이지 탭: 몬스터 체력·공격력을 이 탭의 엔티티 성장 곡선에서 가져오기(지금은 숫자 하나씩).
- 프로젝트 공통 설정·기준안: Kalivra의 스냅샷·비교를 워크벤치 전체로 — 모든 탭이 같은 기준안 저장·비교 형식을 쓰게 한다(앞선 리뷰의 '시나리오 비교' 항목).
- 내보내기: CSV·JSON 먼저, Unity ScriptableObject(C#)는 그다음.

## 7. 실행으로 확인한 동작 (2026-10-18)

v1.0.1 계산 모듈(`calculator.js`, `battle.js`)을 별도 하네스로 Node에서 실행했다(파일·네트워크 접근 없는 순수 계산 모듈, 전부 읽은 뒤 실행). 데미지 변동·특성 없이, 기본 규칙 `a.atk * (100 / (100 + b.def))`, `a.acc - b.eva`.

| 확인한 것 | 설정 | 결과 |
|---|---|---|
| **기본 샘플 프로젝트** | Chicken 대 Godzilla Lv10, 샘플 데미지 수식 `atk * (100 / (100 + def))` | 데미지 0 → 1만 회 모두 200턴 무승부, 승률 0%. 오류를 잡아 0을 돌려주므로 경고 없음 (정적 분석에서 놓쳤던 것) |
| 같은 샘플, 수식 고침 | 같은 Lv10, `a.`/`b.` 접두어 | Chicken 승 2.8% (CP는 Chicken 3,393 대 Godzilla 1,840) |
| 공격 속도 | 같은 스탯, A 공격 속도 1 → 2 → 4 | 승률 49.7% → 66.8% → 79.7%, 한 전투 공격 횟수 20 대 19 — 선공 확률 a/(a+b)만큼 |
| 피격 버프 | 맞을 때마다 방어 +10 | 적중 19회에 버프 38회 (정확히 2배) |
| 무승부 | 서로 못 쓰러뜨리는 두 탱커 | A 승 0%, B 승 0%, 합 0% (평균 200턴) |
| 리그 잡음 | 같은 캐릭터끼리 100회 × 20번 | 42% ~ 58% |
| 아이템 순서 | 공격 100에 +10과 ×2 | 순서대로 120, 순서 바꾸면 110 |
| 명중 하한 | 명중 0 대 회피 100 | 실현 회피율 95.0% (하한 5%) |
| 구간 분석 잡음 | 같은 설정 5번 | 후반 승률 39%~61% |

검증용 기준값(트리거·변동 없음, 40만~140만 회)은 [samples/kalivra-reference.json](samples/kalivra-reference.json)에 숫자만 기록했다. 워크벤치의 "턴 교대" 정확해는 세 경우 모두 3σ 안에서 일치한다(K1 0.8 정확히, K2 0.72643 대 0.72676, K3 0.02640 대 0.02659). 같은 설정을 시간 기반으로 돌리면 K2 98.9%, K3(Chicken 대 Godzilla) 75.1%로, 공격 속도 반영 여부가 결론을 뒤집는다.

**구현 상태**: 채택표 1~5단계(1~4·6~21·24~27)를 구현했다 — 5단계에서 엔진 내보내기(27, Unity ID 문자열·Unreal DataTable 행 배열·수식 C#/C++), 전 탭 공통 스냅샷(11의 나머지), 스테이지 탭 연결. 이후 보류였던 아이템 세트(5)·Undo/Redo(22, 전 탭 공통)·PDF 리포트(28, 브리핑 탭)도 구현해 채택표에서 제외(23·29·30)를 뺀 27개가 모두 들어갔다 — 4단계에서 목표 역산(20)을 점수 목표·최소 변경·민감도·효과 분해까지 — 3단계에서 특성(19)·전투 로그(18)·구간 리포트(13)·전투 기준 감시(12). 특성 기준값 T1(흡혈) 0.46342, T2(공격 직전 ×1.8) 0.41612와 워크벤치 시뮬레이션이 1.4σ 안에서 맞는다. 남은 것은 없다(제외 3개는 그대로 제외).

## 8. 남은 불확실성
- 실행한 것은 계산 모듈(`calculator.js`, `battle.js`)뿐이다. 앱 화면(Electron)은 띄우지 않았고, 리포트(PDF)·그리드 편집·Unity/Unreal 내보내기는 코드로만 확인했다.
- REA 그래프는 정적 분석이라 커버리지가 partial이다(동적 IPC 채널 1개 미해결). 밸런스 계산 모듈(`battle.js`, `calculator.js`, `solver.js`, `renderer.js`의 분석 함수)은 전부 직접 읽었다.
- 1번(공격 속도)은 의도된 단순화일 수도 있다. 다만 기본 CP 수식이 aspd를 곱하고 있어 두 결과가 어긋나는 것은 코드상 사실이다.
