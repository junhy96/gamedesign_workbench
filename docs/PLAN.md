# 기획 워크벤치 — 전체 기획 정리

> 최종 정리일: 2026-10-13 · 상태: 1번 완료, 2~4번 예정

## 1. 한 줄 요약

게임 시스템 기획자가 **엑셀로 풀기 어려운 검증**(확률, 경제, 프레임)을 브라우저에서 바로 돌려보는 도구 모음.
포트폴리오로 공개하고, 면접관과 동료가 **링크 하나로** 열어볼 수 있게 만든다.

## 2. 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 배포 | GitHub Pages + 공개 저장소 | 링크 공유, 코드와 페이지를 함께 보여줌, 무료 |
| 형태 | HTML + 바닐라 JS (ES 모듈), 빌드 없음 | 설치·빌드 없이 그대로 배포. 저장소를 읽는 사람도 구조를 바로 이해 |
| 라이브러리 | Chart.js 4.4.1 (그래프), Mermaid (다이어그램, 사용하는 탭에서만 로드) | CDN 버전 고정 |
| 저장 | localStorage(`planwb:` 접두어) + JSON 내보내기/불러오기 + 공유 링크(`#` 뒤에 설정) | 서버 없음. 같은 github.io 계정의 다른 페이지와 키 충돌 방지 |
| 계산 위치 | 모두 브라우저 안. 무거운 시뮬레이션은 Web Worker | 화면 멈춤 방지, 데이터 외부 전송 없음 (4번 탭의 API 호출만 예외) |
| 검증 | 순수 계산 모듈은 DOM과 분리 → `node --test`로 테스트 | 계산이 맞다는 근거를 README에 제시 |
| 개발 실행 | `npm run dev` (로컬 서버). 파일 더블클릭은 ES 모듈이 막혀 동작 안 함 | |

## 3. 만드는 순서

1. **강화 기대 비용 계산기** — 완료
2. **패턴 프레임 검증기** — 다음. 규모가 작고, 타임라인 시각화로 화면 임팩트가 큼
3. **재화 흐름 시뮬레이터** — 가장 큼. 행동 규칙 설계가 핵심이라 시간을 가장 많이 씀
4. **자연어 다이어그램** — 선택. 공개 페이지에선 데모 모드가 필요해 우선순위 낮음

> 원칙: “완성된 탭 1개”를 먼저 공개하고 하나씩 추가한다. 미완성 탭은 계획 요약만 보여준다.

## 4. 도구별 기획

### 4-1. 강화 기대 비용 계산기 ✅

**왜 필요한가**
성공·실패·하락·파괴 확률, 보호권 같은 규칙을 넣으면 목표 단계까지 기대 비용과 분포를 계산한다.
실패 시 단계가 내려가는 구조는 엑셀로 풀기 까다롭고(사실상 마르코프 체인), 시뮬레이션을 매번 돌리기도 번거롭다.
강화·성장 시스템을 기획할 때 바로 쓰고, **확률 공시용 수치 검증**에도 쓸 수 있다.

**입력**
- 단계별 표: 성공 / 실패-유지 / 실패-하락 / 파괴 확률(%), 1회 비용
- 시작·목표 단계, 파괴 시 복구 단계, 파괴 1회 비용(복구비 또는 장비값)
- 찬스타임(옵션): N회 연속 하락하면 다음 시도 100% 성공
- 이벤트: 상한 단계 이하 파괴 확률 배율(줄어든 만큼 유지로), 비용 배율
- 파괴방지: 단계별 on/off, 추가 비용(기본 비용 대비 %, 할인 미적용)
- 프리셋: 메이플 KMS 일반 장비(비공식 참고값) / 하락+찬스타임 가상 예시 / 직접 입력

**알고리즘**
- 상태 = (단계, 연속 하락 수). 찬스타임을 끄면 연속 하락 수는 항상 0.
- 상태별 **기대 시도 횟수 N**을 연립방정식 `(I − Qᵀ)N = e_start`로 구한다(가우스 소거).
  - 기대 비용 = Σ N × 1회 비용 + 기대 파괴 × 파괴 1회 비용
  - 기대 파괴 = Σ N × 파괴 확률
- **파괴 없이 도달할 확률 q**: 파괴를 ‘실패로 종료’로 보고 별도 연립방정식.
  - 파괴 횟수 분포는 기하분포: `P(D=0)=q시작`, `P(D=j)=(1−q시작)(1−q복구)^(j−1)q복구`
- **파괴방지 최적 조합**: 보호 가능한 단계(최대 10개)의 모든 조합을 정확해로 비교해 기대 비용 최소 조합 추천.
- **몬테카를로**: 시드 고정 2만 회(Web Worker). 비용 분포(중앙값·상위 10%·1%)와 정확해 검산용.
  계산량이 너무 큰 설정(기대 시도 × 반복 수 > 4천만)은 시뮬레이션을 생략하고 정확해만 표시.

**출력**
- KPI: 기대 비용, 파괴 없이 도달할 확률, 기대 파괴 횟수(+운 나쁜 10%·1%), 기대 시도 횟수
- 총 비용 분포 히스토그램 + 분위수
- 단계별 표: 돌파 전 파괴 확률 `b/(s+b)`, 기대 시도, 비용 비중
- 계산 검증 카드: 정확해 vs 시뮬레이션 비교

**검증 결과** (메이플 프리셋, 15성 시작, 파괴 시 12성 복구)

| 목표 | 파괴 없이 도달 | 기대 파괴 | 기대 시도 |
|---|---|---|---|
| 17성 | 88.1% | 0.13회 | 7.7회 |
| 18성 | 61.7% | 0.62회 | 20.8회 |
| 21성 | 21.2% | 3.71회 | 100.9회 |
| 22성 | 11.8% | 7.49회 | 194.8회 |
| 25성 | 0.78% | 127.5회 | 3,149회 |

15→22성 옵션 비교: 기본 11.8% / 파괴방지(15~17성) 19.1% / 샤타 20.5% / 둘 다 29.2% (파괴 없이 도달할 확률)

**알려진 한계와 메모**
- 메이플 수치는 나무위키 정리(2026-10 확인) 기준. 26성 유지 확률은 출처 표기(74.16%)의 합이 100.04%라 74.12%로 보정.
- 복구 규칙은 “12성 복구”와 “직전 단계(최대 22성) 복구”가 공존 → 복구 단계를 입력으로 둠.
- 강화 비용 공식은 할인 전 기준. MVP·PC방 할인은 미반영(이벤트 비용 배율로 근사 가능).
- 이력에 따라 확률이 바뀌는 규칙 중 찬스타임만 지원. 실패 누적 확률 상승·천장은 미지원(상태 확장으로 추가 가능).

### 4-2. 패턴 프레임 검증기 (다음 작업)

**왜 필요한가**
스킬이나 보스 패턴의 선딜·판정·후딜을 프레임 단위로 넣으면, 패턴 사이의 회피 가능 구간과 반격 타이밍이 몇 프레임인지 계산한다.
단순한 그림이 아니라 **“이 연계는 회피 윈도우가 6프레임이라 너무 빡빡하다”** 같은 검증이 목적이다.

**입력**
- 플레이어: 회피 선딜, 무적 프레임, 회피 전체 길이, 공격 발생·후딜, 반응 시간(ms), 입력 지연(프레임)
- 보스 패턴(연계 순서대로): 선딜, 판정 구간(다단 히트는 구간 여러 개), 후딜, **식별 가능 시점**(페이크·딜레이 공격 대비)
- 프레임레이트(30/60fps). 내부 계산은 프레임 단위, 반응 시간은 ms → 프레임 환산

**알고리즘**
- 회피 입력 가능 구간: `[판정 종료 − 회피 선딜 − 무적 + 1, 판정 시작 − 회피 선딜]`
  - 구간 길이 = 무적 프레임 − 판정 지속 + 1 → 0 이하면 구르기로 회피 불가(이동 회피 필요)
- 반응 회피 가능: `식별 시점 + 반응 시간 + 입력 지연 ≤ 최종 입력 시점` → 아니면 **암기 패턴**
- 반격 여유: `다음 판정 시작 − (회피 종료 + 공격 발생 + 공격 후딜 + 회피 선딜)`
  - 처음 아이디어의 식에는 공격 후딜과 다음 회피 선딜이 빠져 있어 “때리고 맞는” 경우도 반격 가능으로 판정됐음 → 보완
- 다단 판정은 구간별로 계산하고 가장 빡빡한 값을 대표값으로

**출력**
- 패턴별 색상 타임라인(선딜·판정·후딜·회피 가능 구간 겹쳐 표시) + 판정 칩(반응 가능 / 암기 / 회피 불가 / 반격 n프레임)
- 기준값(예: 회피 윈도우 8프레임 미만 경고) 설정

**범위 밖**: 공간(사거리·추적·방향). 시간축만 다룬다고 화면에 명시.

### 4-3. 재화 흐름(경제) 시뮬레이터

**왜 필요한가**
재화의 획득처와 소모처를 노드로 연결하고, 유저 유형별로 일 단위 누적을 돌려본다.
“이 이벤트를 넣으면 30일 뒤 골드가 얼마나 쌓이나” 같은 질문에 답하는 용도.
Machinations라는 유료 툴이 있지만 한국어·경량 버전은 비어 있고, 라이브 서비스 시스템 기획 포트폴리오로 설득력이 크다.

**입력**
- 재화, 획득처(일일·주간·이벤트 기간), 소모처(고정·비율), 교환 규칙
- 유저 유형: 비율, 활동량 배수, **행동 규칙**(예: 보유량 X 이상이면 교환·소비) ← 가장 중요한 설계 포인트
- 강화 계산기의 기대 비용을 소모처로 가져오기

**알고리즘**
- 일 단위 이산 시뮬레이션. 하루 처리 순서: 획득 → 교환 → 고정 소모 → 비율 소모 (순서를 화면에 명시)
- 교환 규칙의 순환(A→B→A)은 입력 단계에서 감지해 막고, 하루 교환 횟수 상한
- 편차: **유저별 고정 배수 + 일별 소폭 변동**으로 수백 회 반복 → 상하위 범위를 띠로 표시
  (매일 독립적으로 흔들면 평균으로 수렴해 띠가 비현실적으로 좁아짐)

**출력**
- N일 보유량 추이(유저 유형별), 소모율 = 누적 소모 ÷ 누적 획득
- 적체 경고: 초반 몇 주는 제외하거나, 목표 보유량 곡선 대비로 판정 (0에서 시작해 증가율 경고가 항상 울리는 문제 방지)
- 입력 표에서 Mermaid 흐름도(획득처 → 재화 → 소모처) 자동 생성

**용어**: 가격 변동이 없는 모델이라 엄밀히는 ‘인플레이션’이 아니라 **재화 적체**를 잰다. 유저 간 거래는 범위 밖.

### 4-4. 자연어 다이어그램 (선택)

**개요**: 문장으로 설명하면 Mermaid 코드로 만들고, 코드 편집 + 실시간 미리보기 + 이미지 내보내기.

**공개 페이지 대응**
- 면접관은 API 키가 없음 → **데모 모드**(미리 생성한 예시) 기본, 본인 키 입력 시에만 실제 호출
- 키를 코드에 넣지 않음. localStorage에도 저장하지 않음(같은 도메인의 다른 페이지가 읽을 수 있음)
- 브라우저 직접 호출 시 `anthropic-dangerous-direct-browser-access: true` 헤더 필요

**구현 메모**
- 응답에서 ``` 코드 펜스 제거 후 `mermaid.parse()`로 검증, 오류 시 에러 메시지를 붙여 1회 자동 수정
- `securityLevel: 'strict'` 유지(생성된 코드의 링크·스크립트 차단)
- PNG 내보내기는 `htmlLabels: false`로 렌더해야 캔버스 변환이 깨지지 않음, 한글 폰트 로드 확인
- 템플릿: UI 플로우, 상태 머신, 퀘스트 분기, 시퀀스
