# 기획 워크벤치 — 전체 기획 정리

> 최종 정리일: 2026-10-18 · 상태: 강화·패턴 프레임·가챠 완료, 재화 흐름·수급·방치형 스테이지 성장·스탯 전투 밸런스는 초안(편차·이탈·도구 연결 반영), 다이어그램·PDF는 부가 도구

## 1. 한 줄 요약

게임 시스템 기획자가 **엑셀로 풀기 어려운 검증**(확률, 경제, 프레임)을 브라우저에서 바로 돌려보는 도구 모음.
포트폴리오로 공개하고, 면접관과 동료가 **링크 하나로** 열어볼 수 있게 만든다.

## 2. 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 배포 | GitHub Pages + 공개 저장소 | 링크 공유, 코드와 페이지를 함께 보여줌, 무료 |
| 형태 | HTML + 바닐라 JS (ES 모듈), 빌드 없음 | 설치·빌드 없이 그대로 배포. 저장소를 읽는 사람도 구조를 바로 이해 |
| 라이브러리 | Chart.js 4.4.1 (그래프), Mermaid (다이어그램, 사용하는 탭에서만 로드) | CDN 버전 고정 |
| 저장 | localStorage(`planwb:` 접두어) + JSON 내보내기/불러오기 + 공유 링크(`#` 뒤에 설정) | 서버 없음. 같은 github.io 계정의 다른 페이지와 키 충돌 방지 |
| 계산 위치 | 모두 브라우저 안. 무거운 시뮬레이션은 Web Worker | 화면 멈춤 방지, 데이터 외부 전송 없음 (4번 탭의 API 호출만 예외) |
| 검증 | 순수 계산 모듈은 DOM과 분리 → `node --test`로 테스트 | 계산이 맞다는 근거를 README에 제시 |
| 개발 실행 | `npm run dev` (로컬 서버). 파일 더블클릭은 ES 모듈이 막혀 동작 안 함 | |

## 3. 만드는 순서

1. **강화 확률·비용 설계** — 완료
2. **패턴 프레임 검증기** — 완료
3. **재화 흐름 시뮬레이터** — 초안 (유저 편차 띠·잔존율·LTV, 강화·수급에서 성장 비용 받기)
4. **가챠·수집 설계** — 완료
5. **방치형 스테이지 성장** — 초안 (구간 비용 공식·의도 체류·정체 원인 구간, CSV 가져오기)
6. 부가 도구: **자연어 다이어그램** (PPT 도형 내보내기), **PDF 도구** (별도 페이지 /pdf, [분석 기록](pdf-reference-analysis.md))

> 포트폴리오 초점: 핵심 검증 도구(강화·가챠·수급·스테이지 성장·재화 흐름·프레임)를 앞에 두고, 다이어그램·PDF는 헤더에서 한 단계 낮춰 "부가 도구"로 둔다.
> 도구 결과로 내린 판단은 [case-study.md](case-study.md)에 사례로 정리한다.

> 원칙: “완성된 탭 1개”를 먼저 공개하고 하나씩 추가한다. 미완성 탭은 계획 요약만 보여준다.

## 4. 도구별 기획

### 4-1. 강화 확률·비용 설계 ✅

**왜 필요한가**
강화 시스템의 BM과 밸런스를 설계할 때, 기획자가 **확률과 비용을 직접 조절하면서 기대값을 바로 확인**하는 도구.
특정 게임의 확률을 계산하는 게이머용 계산기가 아니다. 하락·파괴·천장·보조 아이템이 섞이면 엑셀로 정확한 기대값을 구하기 어렵고(사실상 마르코프 체인), 시뮬레이션을 매번 돌리기도 번거롭다.
강화·성장 시스템 기획, BM 아이템 가격 책정, **확률 공시 수치 검증**에 쓴다.

**입력 (모두 기획자가 설계)**
- 단계별: 성공(+1) / **대성공(+2, 이중 강화)** / 유지 / 하락 / 파괴 확률(%), 재화별 1회 비용
- 재화 최대 4종 + 1단위당 원화 환산 가치 (무료 재화도 기회비용으로 환산)
- 파괴: 복구 단계 + 재화별 복구 비용
- 연속 보정(카운터 하나로 통합):
  - 연속 실패 기준 — **천장**(N회 연속 실패 시 확정 성공), **실패 누적 보너스**(%p 또는 기본 성공률 대비 %, 최대 성공률 상한)
  - 연속 하락 기준 — **찬스타임**(N회 연속 하락 시 확정 성공)
- 보조 아이템(BM, 최대 5종): 파괴방지 / 하락방지 / 성공률 증가(%p), 재화별 가격, 적용 단계 범위, 단계별 사용 여부
  - 성공률 증가는 **수량형**도 가능: 개당 +%p, 한 번의 시도에 최대 n개 → 단계 표에 투입 개수 (`items[].mode = 'quantity'`, `usage[단계] = { units: { id: 개수 } }`, 저장 형식 v3 — v2 저장본은 on/off 아이템으로 읽음)
- 이벤트 배율: 성공 ×, 파괴 ×, 비용 ×
- 템플릿 4종: 기본 성장형(하락·파괴) / 실패 누적형(보너스·천장) / 고위험 고보상(이중 강화·찬스타임) / 빈 표

**알고리즘**
- 상태 = (단계, 연속 카운터). 기대값 E는 `(I − P)E = r`.
- 단계 순 정렬 → `I − P` = 띠 행렬 + 파괴 열(rank-1). **띠 LU(피벗 없음, 행 대각 우세)** + **Sherman–Morrison**.
- 분해 하나로: 기대 비용·시도·파괴, 재화별 소모량, **2차 모멘트 → 정확한 표준편차**, 전치 풀이로 **방문 횟수 → 단계별 분해·수반 방법 민감도**, 파괴 없이 도달할 확률(+기하분포), 단계별 돌파 전 파괴 확률(선행 블록 풀이).
- **보조 아이템 최적 사용**: 마르코프 결정 과정. 상태마다 아이템 조합(토글형 0/1 × 수량형 0~최대 개수)을 행동으로 두고 정책 반복법(평가 ↔ 개선)으로 기대 총비용 최소 정책. 효과(파괴방지·하락방지 여부, 성공률 증가 합)가 같은 조합은 가장 싼 것으로 합쳐 행동 수를 줄인다(7,344 → 521).
- **아이템 가격 곡선**: 대상 아이템의 한 재화 가격을 범위로 바꾸며 최적 정책을 다시 풀고, 최종 체인의 우변만 바꿔 BM 기대 매출(아이템 기대 지출)·기대 구매 개수를 구한다. 매출 최대 가격, 유저 절감률(아이템 없이 대비)이 목표 이하가 되는 첫 가격, 없으면 그 이유(대상 아이템이 안 쓰이기 시작하는 가격과 그때의 절감률).
- **목표 비용 역산**: 구간 성공률 배율 α를 로그 스케일 이분 탐색 (단계별 100% 상한, 실패 결과 비율 유지).
- **몬테카를로**: 시드 고정 2만 회(Web Worker) → 분위수, 예산별 도달 확률, 히스토그램.

**출력**
- KPI: 기대 총비용(원), 표준편차·변동계수, 파괴 없이 도달할 확률, 기대 파괴(운 나쁜 10%·1%), 기대 시도 + 기준안 대비 변화율
- 달성 분위별 수치 (2026-10-18): 총비용·시도·파괴의 0.1%~99.9% 분위 막대 그래프 + 표 (`js/lib/quantiles.js`, 가챠와 공용). 각 열은 그 지표만의 분위라 같은 줄이 같은 유저는 아님을 표에 적는다
- 총비용 분포 + 예산 → 도달 확률, 50/90/99% 도달 예산
- 재화별 기대 소모, **보조 아이템 기대 지출(BM 기대 매출)**, 파괴 복구 비용
- 아이템 가격 곡선: 가격별 BM 기대 매출·유저 절감률 그래프(같은 가격 축 두 개), 가격별 표, 매출 최대 가격·목표 절감률 가격 적용
- 단계 표: 돌파 전 파괴, 기대 시도, 비용 비중, 민감도(상위 3단계 강조)
- 확률표 CSV(공시 검토용), JSON 저장/불러오기, 공유 링크

**검증** (`npm test` 22개): 체인과 독립적인 규칙 시뮬레이터와 모든 메커닉에서 일치, 밀집 행렬 풀이와 1e-8 일치, 기하분포 해석해, 민감도 ≈ 유한 차분, 최적 정책 ≤ 수동 조합, 역산 정확도. 수량형·가격 곡선은 `docs/samples/enhance-quantity-items.json`의 전수 탐색 정답(아이템 없이 비용, 최적 비용·정책, 가격 곡선 30개 점, 매출 최대 가격)과 반올림 자리 안에서 일치.

**알려진 한계와 다음 후보**
- 아이템 사용 정책은 상태별(단계 × 카운터). 유저의 예산 제약(예산 안에서 도달 확률 최대화)은 목적 함수가 달라 미지원 → 후보.
- 성공률 증가 아이템은 실패 결과에서 비율대로 차감. 특정 결과만 줄이는 효과(예: 파괴만 절반)는 이벤트 배율로 근사.
- 연속 보정 상태는 최대 300단계(천장 없이 보너스만 있을 때 상한 확인).
- 수량형 최적화는 효과가 다른 조합이 단계당 2만 개를 넘으면 거부(최대 개수를 줄이도록 안내). 가격 곡선은 한 번에 아이템 하나, 재화 하나의 가격만 바꾼다.
- 후보: 단계별 보너스·천장 개별 설정, 계승(실패 시 재료 일부 반환), 예산 제약 최적화, 여러 아이템 가격을 함께 움직이는 가격 곡선.

### 4-2. 패턴 프레임 검증기 ✅

**왜 필요한가**
스킬이나 보스 패턴의 선딜·판정·후딜을 프레임 단위로 넣으면, 패턴 사이의 회피 가능 구간과 반격 타이밍이 몇 프레임인지 계산한다.
단순한 그림이 아니라 **“이 연계는 회피 윈도우가 6프레임이라 너무 빡빡하다”** 같은 검증이 목적이다.

**입력**
- 플레이어: 회피 선딜, 무적 프레임, 회피 전체 길이, 공격 발생·후딜, 반응 시간(ms), 입력 지연(프레임)
- 보스 패턴(연계 순서대로): 선딜, 판정 구간(다단 히트는 구간 여러 개), 후딜, **식별 가능 시점**(페이크·딜레이 공격 대비)
- 프레임레이트(30/60fps). 내부 계산은 프레임 단위, 반응 시간은 ms → 프레임 환산

**알고리즘**
- 회피 입력 가능 구간: `[판정 종료 − 회피 선딜 − 무적 + 1, 판정 시작 − 회피 선딜]`
  - 구간 길이 = 무적 프레임 − 판정 지속 + 1 → 0 이하면 구르기로 회피 불가(이동 회피 필요)
- 반응 회피 가능: `식별 시점 + 반응 시간 + 입력 지연 ≤ 최종 입력 시점` → 아니면 **암기 패턴**
- 반격 여유: `다음 판정 시작 − (회피 종료 + 공격 발생 + 공격 후딜 + 회피 선딜)`
  - 처음 아이디어의 식에는 공격 후딜과 다음 회피 선딜이 빠져 있어 “때리고 맞는” 경우도 반격 가능으로 판정됐음 → 보완
- 다단 판정은 구간별로 계산하고 가장 빡빡한 값을 대표값으로

**출력**
- 패턴별 색상 타임라인(선딜·판정·후딜·회피 가능 구간 겹쳐 표시) + 판정 칩(반응 가능 / 암기 / 회피 불가 / 반격 n프레임)
- 기준값(예: 회피 윈도우 8프레임 미만 경고) 설정

**범위 밖**: 공간(사거리·추적·방향). 시간축만 다룬다고 화면에 명시.

**구현 메모 (완료)**
- 회피 타이밍 가정 2가지: 반응형(가장 늦게 입력) / 최적 입력(동적 계획법: 타격 무리별 회피 1회, 상태 = 다시 행동 가능한 가장 이른 프레임). 반응형에서 실패하고 최적에서 성공하면 “선입력 강제”로 표시.
- 탐욕법(가장 이른 입력)은 한 번의 회피로 연속 타격을 덮는 경우를 놓침 → 브루트포스 테스트로 발견해 동적 계획법으로 교체.
- 암기 판정 시 “몇 프레임 늦는지 / 선딜을 몇 프레임 늘리면 되는지 / 식별 시점을 앞당기라”는 수정 제안까지 문장으로 출력.
- 반격은 공격 발생·전체 길이·회피 캔슬 시점으로 횟수 계산, 연계 반복 옵션.
- 템플릿: 기본 4연계(여유·가혹·암기·불가 한 번에) / 빠른 연계(선입력 강제) / 입문 보스 / 빈 패턴.
- 후보: 다단 판정의 타격별 다른 지속 시간, 방어·패리 판정, 공격 무작위 순서(확률 연계).

### 4-3. 재화 흐름(경제) 시뮬레이터

**왜 필요한가**
재화의 획득처와 소모처를 노드로 연결하고, 유저 유형별로 일 단위 누적을 돌려본다.
“이 이벤트를 넣으면 30일 뒤 골드가 얼마나 쌓이나” 같은 질문에 답하는 용도.
Machinations라는 유료 툴이 있지만 한국어·경량 버전은 비어 있고, 라이브 서비스 시스템 기획 포트폴리오로 설득력이 크다.

**입력**
- 재화, 획득처(일일·주간·이벤트 기간), 소모처(고정·비율), 교환 규칙
- 유저 유형: 비율, 활동량 배수, **행동 규칙**(예: 보유량 X 이상이면 교환·소비) ← 가장 중요한 설계 포인트
- 강화 계산기의 기대 비용을 소모처로 가져오기

**알고리즘**
- 일 단위 이산 시뮬레이션. 하루 처리 순서: 획득 → 교환 → 고정 소모 → 비율 소모 (순서를 화면에 명시)
- 교환 규칙의 순환(A→B→A)은 입력 단계에서 감지해 막고, 하루 교환 횟수 상한
- 편차: **유저별 고정 배수 + 일별 소폭 변동**으로 수백 회 반복 → 상하위 범위를 띠로 표시
  (매일 독립적으로 흔들면 평균으로 수렴해 띠가 비현실적으로 좁아짐)

**출력**
- N일 보유량 추이(유저 유형별), 소모율 = 누적 소모 ÷ 누적 획득
- 적체 경고: 초반 몇 주는 제외하거나, 목표 보유량 곡선 대비로 판정 (0에서 시작해 증가율 경고가 항상 울리는 문제 방지)
- 입력 표에서 Mermaid 흐름도(획득처 → 재화 → 소모처) 자동 생성

**용어**: 가격 변동이 없는 모델이라 엄밀히는 ‘인플레이션’이 아니라 **재화 적체**를 잰다. 유저 간 거래는 범위 밖.

**구현 메모 (2026-10-17)**
- 편차 띠: 유저별 고정 배수(로그정규 σ, 평균 1) × 일별 변동으로 세그먼트당 N명 → 날짜별 전투력 하위·상위 10%. 하위 10%가 콘텐츠를 7일 이상 늦게(또는 못) 열면 경고.
- 이탈: 세그먼트별 D1·D7·D30 잔존율 → 구간별 멱법칙 잔존 곡선. 성장 시뮬레이션은 바꾸지 않고, 콘텐츠 해금일의 잔존율(30% 미만 경고)과 설치당 매출(LTV)을 계산.
- 무제한 콘텐츠는 콘텐츠 단계 안에서 전투력이 변하지 않으므로 횟수를 한 번에 계산(편차 계산 속도 확보).
- 강화 탭 → '재화 흐름으로 보내기': 단계별 재화 기대 소모(방문 횟수 × 시도 비용)를 성장 항목 비용 표로. 수급 탭과 같은 경로(applyGrowthTable).
- 성장 루프 다이어그램 (2026-10-18): Mermaid 자동 배치는 묶음 사이 선이 상자를 가로지르고 교환·되먹임 선이 겹쳐 읽기 어려워 직접 배치로 교체.
  열 순서는 무게중심 정렬 → 이웃 두 노드 교환으로 교차가 줄면 유지(국소 탐색). 교환 상점은 두 재화 사이에 끼워 세로 화살표, 되먹임은 맨 위 통로.
  노드는 종류(콘텐츠·과금·재화·상점·성장·전투력)별 색, 재화를 나르는 선은 그 재화의 색. 기본 도형만 써서 PPT 도형 변환을 그대로 쓴다.
- 남은 후보: 세그먼트 이동(무과금 → 과금 전환), 기간 한정 이벤트, 재화 단위 몬테카를로(띠를 보유량에도).

### 4-5. 가챠·수집 설계 ✅

**왜 필요한가**
수집형·방치형 기획서의 뽑기 비용은 대부분 `필요 장수 ÷ 확률`로 계산한다. 이 값은 (1) 소환 레벨처럼 처음엔 확률이 낮은 구간과 (2) 이미 다 모은 유닛이 또 나오는 중복을 빼먹어서, 목표가 클수록 실제보다 크게 낮다.
방치형 기획서의 "레전드 n장 = (1 ÷ 확률) × n회" 계산을 검토하다 시작했다 — 예를 들어 같은 동료 6장씩 5종(30장)이 필요하면 중복 때문에 평균 약 45장(≈ +50%)을 뽑아야 한다.

**입력**: 등급(확률·종 수·중복 조각·교환 가격), 소환 레벨별 확률표, 천장(확정·확률 상승), 픽업(비율·보장), 마일리지, 목표(수집 K종 × k장 / 픽업 k장 / 특정 캐릭터 k장), 캐릭터 이름, 기준 유저(무과금 획득·월 과금)

**알고리즘**
- 시뮬레이션: 목표 등급 당첨까지 기하분포로 건너뛰기, 확률이 바뀌는 지점(레벨 경계·천장 상승 구간·교환 가능 시점)에서만 끊음. 다른 등급 중복 조각은 뽑기당 기대값.
- 정확해 ① 수집(고정 확률·교환 없음): 포아송화 `E[N] = (1/λ)∫ 1 − P(k,u)^K du`.
- 정확해 ② 픽업·특정 캐릭터(분해 교환 없음): (모은 장수 × 천장 카운터 × 보장) 상태 분포 동적 계획법 → 분포 전체. 마일리지는 결정적 시점의 1장 추가로 반영. 픽업이 아닌 캐릭터는 보장 상태에서 0, 아니면 (1 − s)/(n − 1).
- 확률 공시표(2026-10-18): 소환 레벨별 등급·캐릭터 확률, 천장 변동표(n번째 확률·누적), 실효 확률(1 ÷ 최상위 1장당 평균 뽑기, 픽업 보장이면 (2 − s)장당 1장), 조건 문장. 표시 반올림 검사와 CSV.
- 원인 분해: 같은 설정에서 목표 등급을 1종으로 묶은 "중복 없는 경우"를 따로 계산 → 단순 계산 → 확률 구조 → 중복.

**출력**: 목표별 기대 비용·분위수·단순 계산 대비 배수·도달 기간, 달성 분위별 수치(뽑기·비용·무과금 도달일·천장 구간 당첨, 0.1%~99.9% — 확률 상승이 있으면 확정 천장까지 가는 일은 템플릿 기준 0.002%라 확정 천장만 세면 늘 0이 되어 '천장 구간 당첨'으로 셈), 확률 공시표(캐릭터별 확률과 1장 기대 뽑기), 달성 확률 곡선·예산, 원인 분해·획득 경로, 정확해 대 시뮬레이션 검증, 검증 문장

**범위와 한계**
- 목표마다 처음부터 따로 뽑는다고 계산(천장 카운터·마일리지 0에서 시작). 여러 목표를 한 계정에서 순서대로 진행하는 경우는 후보.
- 천장 확률 상승은 최상위 등급에만 적용하고, 다른 등급 목표 계산에서는 무시(상승분은 최하위 등급에서 빠진다고 가정).
- 합성(같은 등급 n장 → 상위 등급 확률 합성)은 조각 교환으로 근사. 정확한 합성 규칙은 후보.
- 후보: 가중치가 다른 수집(알파벳·스티커 이벤트처럼 종마다 확률이 다른 경우), 10연차 보너스, 계정 진행 순서 시뮬레이션.

### 4-6. 방치형 스테이지 성장

**왜 필요한가**
예전에 서비스한 방치형 게임은 성장을 **챕터-스테이지 기준 드랍, 구간별 강화 비용, 의도 체류 시간**으로 설계했다. 레벨이 수십만까지 가고 시간 단위가 '스테이지에 머무는 초·분'이라, 일 단위·레벨 수십 개를 전제로 한 수급·재화 흐름 탭으로는 이 구조를 다룰 수 없다.
기획서에서 비용 구간 하나의 증가폭을 잘못 잡으면 몇 챕터 뒤에 갑자기 몇 배씩 머무는 정체가 생기는데, 엑셀 레벨별 표(수십만 행)로는 어느 구간 탓인지 찾기 어렵다.
실제 게임 수치는 쓰지 않고, 가상 수치 샘플(`docs/samples/stage-idle-growth.json`)을 기준으로 삼는다 — 5천~2만 레벨 구간을 일부러 가파르게 둬 16~17챕터 정체가 나오게 만든 예시.

**입력**: 챕터 × 스테이지, 몬스터 체력·웨이브 골드(첫 값 × 스테이지당 배수), 공격력(기본 + 레벨당), 웨이브 제한·시간·돌파 웨이브 수, 골드 강화 비용 구간(`LV_MIN, LV_MAX, INIT_COST, STEP`, 마지막 끝 없음), 의도 체류(1챕터 초 × 챕터 배수), 정체 기준

**알고리즘**
- 필요 레벨: 공격력 × 제한 시간 ≥ 몬스터 수 × 체력인 최소 정수 레벨
- 누적 비용: 구간별 등차수열 합 → 레벨별 표 없이 O(구간 수)
- 실제 체류 = max(두 필요 레벨 사이 강화 비용 ÷ 앞 스테이지 초당 골드, 돌파 웨이브 시간), 정체 = 실제 > 기준 × 의도
- 원인 구간 (2026-10-18 교체): 처음에는 "증가폭이 앞뒤 구간보다 크면 원인 후보"였으나, 구간마다 시작 비용·레벨 규모가 달라 숫자 비교가 영향 크기를 말해 주지 않고 첫·마지막 구간은 잡을 수 없었다. 샘플에서 체력 증가율을 0.1%(배수 기준)만 올려도 총 소요 +43%, 정체 54곳인데 문제 구간 증가폭 −10%는 −2.6%뿐 → **반대 가정**으로 교체: 정체 스테이지가 올리는 구간을 이웃처럼 바꿔(증가폭 = 이웃 중 낮은 쪽, 끊긴 시작 비용 = 이어 붙임) 다시 계산하고, 대상 정체가 절반 이상 풀리면 원인
- 정체 원인 · 민감도 카드: ① 해소에 필요한 최소 변경(레버 하나씩 로그 이분 탐색) ② 토네이도(±5/10/20%, 증가율은 증가분 기준, 로그 배율 막대). 대상 정체 = 2곳 이상 몰린 챕터의 정체(정수 올림 단발 정체 제외)
- 증가율 입력은 %(0.01%p 단위). 배수 입력 step 0.01은 화살표 한 번에 증가분이 25%씩 바뀌어 너무 거칠었다. 입력 중 왼쪽 메뉴를 다시 그려 포커스를 잃던 문제도 요약 글자만 갱신하도록 고침

**출력**: 실제 vs 의도 체류 그래프(정체 기준선), 누적 시간, 필요 레벨·구간 경계 그래프, 구간 표 계산 칸(끝 비용·합계·경계 끊김·요구 스테이지·정체 수), 챕터별 표, 검증 문장(원인 적용 버튼), 정체 원인·민감도 카드

**큰 수 표시**: 만·억·조·경 두 단위(`25억 7,633만`) 기본, 지수(`2.58e9`) 선택. 1해(10²⁰) 이상은 한국식에서도 지수 — 방치형 후반 재화는 '해·자' 단위까지 가는데 기획자도 읽기 어렵기 때문.

**저장 형식**: JSON 저장 = `{ schemaVersion, tool: 'stage', description, model, state }` (샘플 파일과 같은 형식, 불러오기는 `state`만 있는 파일도 받음). CSV는 `LV_MIN,LV_MAX,INIT_COST,STEP`, 빈 LV_MAX = 끝 없음. 열 이름이 다르면 별칭으로 자동 매핑하고 화면에서 바꿀 수 있다.

**범위와 한계**
- 골드 하나·강화 하나로 단순화. 장비·동료 등 다른 성장 축과 오프라인 보상·광고 보상 배수는 후보.
- 필요 레벨을 정수로 올림하므로 초반(1-3 같은)에 단발 정체가 생길 수 있다 → 1곳짜리 정체는 '주의'로 낮춰 표시.
- 후보: 의도 체류에 맞춘 구간 증가폭 역산, 챕터별 의도 체류 직접 입력, 재화 흐름 탭으로 보내기.

### 4-7. 스탯·전투 밸런스 (2026-10-18, 초안)

**왜 필요한가**: 캐릭터 스탯·성장을 엑셀 CP 수식으로만 보면 "CP는 높은데 실제로는 진다"를 놓친다. 밸런스 툴 Kalivra를 REA로 분석하고 엔진을 직접 실행해 동작을 확인한 뒤([kalivra-analysis.md](kalivra-analysis.md)), 채택표 1~2단계를 이 저장소 방식(정확해 우선·오차 명시)으로 다시 만들었다.

**입력**: 스탯 정의(성장 선형·등비·표 보간, 최소·최대), 엔티티(기본값·성장값·데미지 변동), 아이템 수정자(고정·%·배율, 순서 무관), 규칙 수식 7개(안전한 파서), 전투 방식(시간 기반 / 턴 교대), 명중 하한·상한, 반올림, 최대 시간·턴

**알고리즘**
- 공격 횟수 분포: (일반 적중 수, 치명 수) 상태 동적 계획법, 계산량(상태 × 공격 수)이 4천만을 넘으면 시뮬레이션으로
- 1:1: 두 공격 횟수가 독립이라 시간 기반·턴 교대 모두 합 하나로 정확해. 같은 시각 결정타는 동전·무승부
- 데미지 변동이 있으면 시뮬레이션(시드 고정) + Wilson 95% 구간
- 승률 행렬은 쌍마다 한 번, 엔티티 점수 = (승 + 무/2) 평균, CP와 점수의 스피어만 상관, CP 역전 쌍(승 − 패 < −10%p, 시뮬레이션이면 구간이 50%를 걸치지 않을 때)

**검증**: 턴 교대 정확해 = Kalivra v1.0.1 엔진 실행 결과(`docs/samples/kalivra-reference.json`, 3σ), 시간 기반 정확해 = 자체 시뮬레이션, 음이항 해석해 등 20개

**3단계 (2026-10-18)**: 특성(발동 시점 8종 × 확률 × 체력 조건 × 최대 발동, 효과 5종) — 전투 한 번을 진행하는 엔진(battleOnce) 하나로 시뮬레이션을 통일하고, 특성이 없을 때는 정확해와 결정타 순서·동시 처리가 같게 맞춤. 전투 로그 20전투·특성 발동 통계, 구간 리포트(레벨별 행렬 → 구간 평균, 계산 예산 6만 전투, 레벨을 나눠 비동기 계산), 전투 기준 감시(구간 지배·같은 1위·구간 변화·상성 순환), Kalivra 특성 가져오기. 특성 기준값은 Kalivra에 버그가 없는 흡혈·공격 직전 배율 두 가지로 엔진을 실행해 만들었다(회복을 Kalivra처럼 내림하지 않았던 차이를 이 비교로 찾아 반올림 규칙을 회복·추가 데미지에도 적용).

**4단계 (2026-10-18)**: 밸런스 도구 카드 — 점수(승 + 무/2) 목표 최소 변경(스탯 배율 로그 이분 탐색, 숨은 수정자 ×k로 계산하고 적용 때 b·g·표에 곱함), 민감도 토네이도(대상·상대 스탯 ±%), 아이템·특성 효과 분해(하나씩 끔), 목표 역산(CP·초당 데미지·점수 → 성장값·기본값·배율). 정확해 점수는 계단 함수라 "목표를 처음 넘는 값"을 돌려준다. 시뮬레이션 쌍은 같은 시드로 비교.

**다음 (채택표 5단계)**: 전 탭 공통 기준안·스냅샷, 스테이지 탭과 연결(몬스터 성장 곡선), 엔진 내보내기(Unity ID 문자열·Unreal DataTable 행 배열)
